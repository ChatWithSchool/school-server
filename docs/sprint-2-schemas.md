## חלק א': סכמות ו-seed

### מה זה בכלל

- **סכמה (מודל):** החוקים של אוסף במסד. אילו שדות יש בכל רשומה, מאיזה סוג הם, מה חובה ומה ייחודי. היא נכתבת בקוד, ב-`model.ts`, ו-Mongoose בודק לפיה כל רשומה לפני שהוא שומר אותה.
- **seed:** קוד שממלא את המסד בנתוני דוגמה קבועים. בזכותו המסך מציג נתונים כבר בהרצה הראשונה, וכל הצוות רואה את אותם נתונים.

### שלב 1: לגלות מה את צריכה לבנות

פותחות את `SPEC.md` של כל אחד משני המסכים שלך (בריפו של הקליינט, `src/screens/<מסך>/SPEC.md`), וקוראות את הסעיף **"אוספים (Mongoose)"**. יש בו עד שלוש שורות:

| השורה ב-SPEC                                   | מה זה אומר                                                      | מה עושות                                                                                  |
| ---------------------------------------------- | --------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| **בבעלות המסך**                                | אוסף שרק המסך שלך משתמש בו                                      | **בונות אותו:** מודל ו-seed במודול שלך                                                    |
| **אוספים משותפים שהמסך אחראי על הכתיבה אליהם** | אוסף שכמה מסכים קוראים ממנו. המודל וה-seed שלו כבר מוכנים בליבה | **לא בונות אותו.** מייבאות אותו מ-`src/models`. את ה-endpoints שכותבים אליו תבני בסרבר ב' |
| **נקראים**                                     | אוספים שהמסך רק קורא מהם                                        | מייבאות אותם מ-`src/models`                                                               |

**לא כתוב אצלך אף אוסף ב"בבעלות המסך"?** זה המצב בעשרה צמדים, וזה בסדר. העבודה שלך בחלק א':

1. לעבור על המודלים בליבה שהמסך שלך קורא (`src/models/*.model.ts`), ולוודא שיש בהם כל שדה שהמסך צריך.
2. להריץ `npm run seed`, ולבדוק בתוסף שיש מספיק נתונים להציג את המסך בכל המצבים שלו (רשימה מלאה, ריקה, ערך חסר).
3. אם חסר שדה במודל של הליבה, או שחסרים נתוני דוגמה למצב מסוים: **לא משנות את הליבה בעצמך.** כותבות לראשת הצוות ב-Slack מה חסר ולאיזה מסך.
4. כשהכול מוכן, ממשיכות לחלק ב' (אם זה המסלול של השבוע), או עוזרות לחברה מהצוות.

### שלב 3: המודל (`model.ts`)

מתחילות מהחוזה ב-`openapi/openapi.yaml`, שמגדיר מה השרת מחזיר. השדות במודל צריכים להתאים לחוזה, ובנוסף יש בהם שדות פנימיים כמו `institutionId`.

```ts
import { Schema, model, type InferSchemaType } from 'mongoose';
import { DATE_ONLY } from '../../utils/dateOnly';

const fooSchema = new Schema(
  {
    // 1. כל אוסף שייך למוסד, עם אינדקס
    institutionId: { type: Schema.Types.ObjectId, ref: 'Institution', required: true, index: true },
    // 2. הפניה לאוסף אחר: ObjectId עם ref לשם המודל שלו
    barId: { type: Schema.Types.ObjectId, ref: 'Student', required: true },
    name: { type: String, required: true, trim: true },
    // 3. רשימה סגורה של ערכים: enum
    status: { type: String, enum: ['open', 'closed'], default: 'open' },
    // 4. תאריך בלי שעה: מחרוזת YYYY-MM-DD
    day: { type: String, required: true, match: DATE_ONLY },
    // 5. שדה שיכול להיות ריק: null, ולא שדה שחסר
    note: { type: String, trim: true, default: null },
  },
  { timestamps: true, collection: 'foos' }, // 6. createdAt ו-updatedAt
);
// 7. מה שאסור שיחזור פעמיים: אינדקס ייחודי
fooSchema.index({ institutionId: 1, name: 1 }, { unique: true });

export type FooDoc = InferSchemaType<typeof fooSchema>;
export const Foo = model('Foo', fooSchema);
```

דוגמאות אמיתיות בפרויקט: `src/models/room.model.ts` (פשוט), ו-`src/models/attendanceRecord.model.ts` (תאריך, `null` ואינדקס ייחודי על כמה שדות).

### שלב 4: ה-seed (`seed.ts`)

```ts
import { Institution, Student } from '../../models';
import { Foo } from './model';

/** Demo data for the screen. Idempotent: running it twice changes nothing. */
export async function seed(): Promise<void> {
  const inst = await Institution.findOne({ name: 'בית ספר לדוגמה' });
  if (!inst) return;
  const students = await Student.find({ institutionId: inst._id }).sort({ nationalId: 1 }).limit(3);
  const items = [
    { name: 'foo', status: 'open', day: '2026-10-20' },
    { name: 'bar', status: 'closed', day: '2026-10-21' },
  ];
  for (let i = 0; i < items.length; i++) {
    await Foo.updateOne(
      { institutionId: inst._id, name: items[i].name }, // the natural key: what identifies the record
      { $set: { ...items[i], institutionId: inst._id, barId: students[i]._id } },
      { upsert: true },
    );
  }
}
```

ה-seed של המודול רץ לבד ב-`npm run seed`, אחרי ה-seed של הליבה ושל האוספים המשותפים. לכן מותר לו לקרוא מכל מה שב-`src/models`.

## הכללים החשובים

### במודל

| כלל                                                                  | למה                                                                                 |
| -------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `institutionId` חובה ועם אינדקס בכל אוסף                             | כל שאילתה מסוננת לפי מוסד, כדי שמוסד אחד לא יראה נתונים של מוסד אחר                 |
| שדות כמו בחוזה, באותם שמות ובאותם ערכי `enum`                        | הקליינט נבנה על Mock לפי החוזה. כל הבדל ישבור את המסך בספרינט 4                     |
| תאריך בלי שעה נשמר כ-`'YYYY-MM-DD'` (`DATE_ONLY` מ-`utils/dateOnly`) | ל-`Date` יש גם שעה ואזור זמן: חצות בישראל הוא עדיין היום הקודם ב-UTC                |
| שדה שיכול להיות ריק מקבל `default: null`                             | הקליינט בודק `=== null`. שדה שחסר לגמרי (`undefined`) יעבור את הבדיקה בלי שתשימי לב |
| `ref` לשם המודל (`'Student'`, `'SchoolClass'`), לא לשם האוסף         | כך Mongoose יודע לאיזה מודל לקשר                                                    |
| אינדקס ייחודי על מה שאסור שיחזור (`unique: true`)                    | המסד חוסם כפילויות גם כשיש באג בקוד                                                 |
| מידע רגיש לא חוזר מהשרת (`select: false`)                            | למשל hash של טוקן או סיסמה. ראו `src/models/invite.model.ts`                        |

### ב-seed

| כלל                                                                                            | למה                                        |
| ---------------------------------------------------------------------------------------------- | ------------------------------------------ |
| **אידמפוטנטי:** `updateOne(..., { upsert: true })` לפי מפתח טבעי, ולא `create` או `insertMany` | אפשר להריץ שוב ושוב בלי כפילויות           |
| **קבוע:** בלי `Math.random()`, ובלי ערכים שמשתנים מהרצה להרצה                                  | כל הצוות רואה אותם נתונים, והבדיקות יציבות |
| **מציג את כל המצבים:** ריק, מלא, ערך חסר, סטטוסים שונים                                        | כך אפשר לבדוק את כל המצבים של המסך         |
| **רק מוסד הדוגמה:** מוצאות אותו לפי `name: 'בית ספר לדוגמה'`                                   | לא נוגעות בנתונים אחרים במסד               |
| **לא מוחקות נתונים של אחרים**                                                                  | ה-seed שלך כותב רק לאוספים שלך             |

### בקוד

| כלל                                                                                                                   | למה                                                        |
| --------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| **מייבאות רק מהליבה ומהתיקייה שלך.** אסור `import ... from '../other-module/...'`                                     | כך אין תלות בצמד אחר. ESLint חוסם את זה, ו-PR כזה לא ימוזג |
| **לא משנות קבצים משותפים** (`src/models`, `src/seed`, `permissions`, `middleware`, `openapi`) בלי אישור של ראשת הצוות | כולן נשענות עליהם. שינוי בהם עובר דרך ראשת צוות            |
| **החוזה לא משתנה לבד.** שינוי ב-`openapi.yaml` עובר בפגישת ראשי הצוותות                                               | הקליינט והשרת חייבים לדבר באותה שפה                        |

## חלק ב': סרבר א' (endpoints לקריאה)

מתחילות רק אחרי שה-PR של חלק א' מוזג.

1. **מוצאות את ה-GET שלך בחוזה.** ב-`openapi/openapi.yaml` מחפשות את מזהה המסך שלך. בכל endpoint כתוב `x-screens` (אילו מסכים משתמשים בו) ו-`x-devs` (מי אחראית עליו). בונות רק את ה-GET שהשם שלך מופיע בהם.
2. **כותבות את ה-route ב-`routes.ts`** (התבנית כבר שם):
   - `authorize('<מסך>', 'read')` בראש כל route.
   - סינון לפי `institutionId: req.user!.institutionId` בכל שאילתה.
   - עימוד עם `parsePagination` ו-`toPage` כשהתגובה בחוזה היא `*Page`.
   - **ממפות כל רשומה לצורה שבחוזה:** `id: String(doc._id)`, ובלי שדות פנימיים כמו `institutionId`.
3. **בדיקה:** לפחות בדיקה אחת לכל endpoint: בלי טוקן מקבלים 401, ועם טוקן התגובה במבנה של החוזה.
4. **בודקות ידנית** עם `curl`, לפי [new-module.md](new-module.md#איך-בודקים-endpoint-ידנית).

את הכתיבה (POST, PUT ו-DELETE), את הולידציה ב-`schema.ts` ואת ההרשאות המלאות עושות בסרבר ב', בספרינט 3.

### הגדרת "הושלם" לחלק ב'

- [ ] עימוד, מיון וסינון לפי החוזה
- [ ] בדיקת הרשאה (`authorize`) וסינון לפי מוסד
- [ ] בדיקה לכל endpoint, ו-`npm run verify` ירוק
